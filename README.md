# Mollix Job Radar — MVP V1

Бесплатный Python-бот, который раз в запуск читает публичные фриланс-заказы,
оценивает их под профиль исполнителя и отправляет новые подходящие проекты
одному владельцу в личный чат Telegram. Никаких платных AI API, сервера,
Docker, базы данных или Redis для работы бота не требуется.

Это периодическая CLI-задача, а не постоянно работающий Telegram-сервер.
Бот не отвечает заказчикам и не публикует отклики: он готовит черновик для вас.

## Быстрый старт

Нужен Python 3.12. Выполняйте команды из корня этого проекта.

Windows PowerShell:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m jobradar check
```

Linux / macOS:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m pytest -q
python -m jobradar check
```

`check` не требует токена, не отправляет сообщения и не меняет state.
Для ручных повторных сетевых проверок выдерживайте примерно 10 минут.
Повторять офлайн-проверки можно без ограничения:

```bash
python -m jobradar check --fixtures tests/fixtures --now 2026-09-21T12:00:00+00:00 --preview
python -m jobradar check --json
python -m jobradar check --verbose
python -m jobradar check --top
python -m jobradar check --top --json
python -m jobradar check --watchlist
python -m jobradar check --watchlist --json
```

Обычный `check` показывает все FIRE/GOOD и максимум пять ближайших SKIP.
`check --top` показывает только FIRE/GOOD, максимум 10: score DESC, age ASC,
responses ASC; неизвестное количество откликов идёт последним при равенстве
первых двух ключей. `--top` имеет приоритет над `--verbose`.
`--top` сохраняет диагностические GOOD 6 и уже известные state проекты;
допуск к отправке показывается отдельно, это не список будущих отправок.
`--watchlist` выбирает GOOD 6 и прошедшие relevance gate проекты с STACK_MISMATCH
(включая SKIP). Он совместим с `--json`, сортируется так же, не ограничен десятью
карточками и не совмещается с `--top`. Hard gates видны и продолжают действовать.
Каждая карточка содержит source, source_id, title, direct_url, published_at,
age_hours, budget, responses_count, score, decision, reasons и risk_flags.
Дополнительно видны подтверждение/доказательство публикации и статус заказа.
Каждый Assessment также содержит `stack_compatibility`, `stack_details`,
`stack_reason`, `complexity`. В текстовом выводе: `STACK_COMPATIBILITY`,
`STACK_DETAILS`, `STACK_REASON`, `COMPLEXITY`; совместимость видна и в preview.
`TELEGRAM_DELIVERABLE` и `DELIVERY_BLOCKERS` объясняют допуск к отправке;
в JSON это `telegram_deliverable` и `delivery_blockers` внутри assessment.
`--verbose` показывает все SKIP. `--json` выводит полный машинный результат,
а вместе с `--top` — только выбранные десять карточек:
нормализованные проекты, баллы, причины, флаги, возраст и признак наличия в state.
`--preview` выводит HTML уведомлений без отправки. `--now` разрешён только с fixtures.

Вывод начинается с SOURCE SUMMARY для всех настроенных источников, включая disabled.
Для каждого есть `fetched`, `parse_errors`, `fresh_count`, `relevant_count`,
`eligible_count`, статус `ok`/`partial`/`error`/`disabled`, число прочитанных страниц
и ошибки отдельных страниц. Эти метрики считаются до cross-source дедупликации;
повторы source_id/URL между страницами одного источника уже удалены.
`filtered_count` — отдельно пропущенные вакансии FL.ru и посты без текста, с учётом
повторов между страницами. Реклама/обучение/full-time в Telegram остаются учтёнными
в fetched, но получают SKIP до scoring.

Общий summary: `total_fetched`, `unique`, `fresh`, `relevance_pass`, `eligible`,
`FIRE`, `GOOD`, `discovery_duplicates`, `duplicates` (найдены в state), `sent`,
`source_metrics`, `source_errors`, `source_error_codes`. `fetched`/`checked` сохранены
как алиасы total_fetched/unique. `checked_at` — момент оценки в UTC после discovery.
Fresh учитывает только подтверждённые исходной биржей даты. Fresh и relevance — независимые признаки, их
пересечение и бюджет/score определяют eligible. `eligible` включает подходящие
записи, уже найденные в state, но повторная отправка по source:id, fingerprint
или нормализованной ссылке запрещена. В summary дополнительно видны
`pagination_skipped`, `details_fetched`, `detail_errors` по каждому источнику.
`telegram_deliverable` — число новых кандидатов, прошедших все delivery gates и
дедупликацию, до ограничения числа сообщений за запуск. `filtered_by_competition`
и `filtered_by_stack` — число eligible, заблокированных соответствующим delivery gate;
неизвестное количество откликов тоже блокирует competition gate.
`filtered_by_open_status` — число eligible без подтверждения приёма откликов:
им запрещён FIRE, но GOOD 7 может пройти delivery. Три счётчика независимы,
могут пересекаться, включают дубликаты state и не суммируются в общее число исключений.
Метрики — снимок на `checked_at`; непосредственно перед отправкой допуск пересчитывается.

## Источники

### Final safety gate

- Отсутствующая, неподтверждённая, противоречивая или будущая дата — SKIP.
  Freelance.ru: только точный timestamp `title` у значка часов карточки.
  FL.ru: только явное «Опубликован ДД.ММ.ГГГГ в ЧЧ:ММ» исходной карточки,
  привязанной к тому же ID. Относительное время ленты не разрешает отправку.
  Даты источников читаются в МСК, хранятся в UTC; точность — минута.
- Возраст >24 часов — SKIP, >6 часов — максимум GOOD (7/10).
  Конфигурация может ужесточить эти пределы, но не расширить их.
  Возраст пересчитывается после discovery и непосредственно перед отправкой.
- Известные статусы «исполнитель выбран/определён», «проект закрыт»,
  «отклики не принимаются» — SKIP. Неизвестный статус виден как
  `OPEN_STATUS_UNKNOWN` и ограничивает оценку до GOOD 7. FIRE требует `open`
  вместе с evidence адаптера: например, доступная кнопка `reply_offer` на FL.ru.
  Скрытая или отключённая кнопка подтверждением не считается. Статус может
  измениться после загрузки исходной карточки.
- Уведомление ведёт только на проверенный путь карточки исходной биржи с тем же
  source_id. Категории, поиск, агрегаторы и Telegram-посты не заменяют карточку.
  Дата Telegram-репоста не подтверждает публикацию заказа; такие записи участвуют
  в discovery/dedup, но сами не проходят gate. Неверифицированный Habr parser
  также не выставляет publication_confirmed.
- Публичные GET ограничены, соблюдают robots и паузы, без входа, CAPTCHA-обхода
  и раскрытия коротких ссылок. Safety gate не включает отправку автоматически.

Публичный фильтр Freelance.ru проверен 23 сентября 2026 года: форма `GET /task`,
поле `c[]`, значение `4` — «Веб-разработка и IT», строка поиска `q`. Все поиски
проверены: telegram, python, api, автоматизация, парсинг, 1с, javascript, react,
backend, devops. Поиски не ограничиваются IT-категорией, чтобы видеть технические
задачи, размещённые в других разделах. Каждая страница проходит существующий gate.
Ссылки трёх разделов FL.ru взяты из публичной ленты и также проверены без входа.
Пагинация FL.ru следует только реально найденным ссылкам `page-2/`, `page-3/`
в пределах того же раздела и хоста. Лимит 3 включает первую страницу.
Freelance.ru тоже поддерживает максимум 3 страницы на поиск, но действующий
robots.txt запрещает `?page=`/`&page=`: HTTP-запросы этих страниц не выполняются,
причина отражается в `pagination_skipped`. URL страниц не угадываются.
При сбое отдельной страницы сохраняются остальные
результаты. После 401/403/challenge другие страницы того же источника не пробуются.

Каналы по умолчанию: freelansim_ru, digitaltender, job_for_bots, freelancetaverna.
Список находится в config/`.env.example`, не в parser. Читается последняя доступная
порция каждого web preview, без вступления в канал. У постов сохраняются `channel`,
исходный URL, timezone-aware timestamp и внешняя ссылка, если есть. Budget — только
из явно подписанной строки, иначе неизвестен. Реклама, обучение и обычные full-time
вакансии без признаков проектной работы получают отдельную причину SKIP.

Habr: защищённая/запрещённая лента не запрашивается. Подготовленный HTML parser
проверен **только на синтетическом контракте**, актуальная живая разметка не
подтверждена. После восстановления публичного доступа нужна повторная проверка
разметки и категорий. Сейчас Habr не считается подключённым источником заказов;
читается только robots.txt. Можно отключить проверку через HABR_FREELANCE_ENABLED=false.
Для потенциальных FIRE/GOOD на FL.ru читается публичная исходная карточка,
чтобы отличить публикацию от поднятия в ленте. Внутренние API не используются.
Возможность откликнуться и тарифы определяются самой биржей.

Перед чтением каждого сайта проверяется его публичный `robots.txt`. Поддерживаются
Allow/Disallow, `*`, `$`, приоритет наиболее длинного правила, Crawl-delay и
Request-rate. Запрещённая лента пропускается. Если robots.txt недоступен из-за
сбоя или запрета, сайт также пропускается; 404/410 трактуются как отсутствие правил.

При текущих robots — до 11 страниц Freelance.ru, 9 discovery + 20 карточек FL.ru,
4 Telegram и один robots.txt
на каждый из четырёх хостов (Habr останавливается на robots). Между запросами
к одному хосту — минимум две секунды, либо больший интервал из robots.txt.
User-Agent: `MollixJobRadar/0.1 (+public freelance listings; no login)`.

Нет авторизации, cookies пользователя, обхода CAPTCHA, ротации прокси или
маскировки браузером. Полученные cookies не пересылаются. Redirect не выполняется:
если площадка снова изменит адрес, требуется явно обновить адаптер.
401/403 и challenge-страницы не обходятся. Временные сетевые ошибки и
429/500/502/503/504 допускают до трёх попыток с backoff. Retry-After больше
30 секунд означает пропуск до следующего запуска. Чтение ограничено таймаутами,
45 секундами на тело ответа, 2 MiB для HTML и 256 KiB для robots.txt.

Ошибка источника отражается в `source_errors`, `source_error_codes` и логах,
но сама по себе не меняет код завершения (даже если не сработал ни один источник).
Повреждённая карточка пропускается отдельно; неизвестная разметка даёт ошибку
источника. Проверяйте summary: код `0` не гарантирует полноту данных.
Ошибка доставки даёт код `1`; ошибка конфигурации, state или CLI — `2`.

## Архитектура и модель

```text
CLI → public HTTP + robots.txt → независимые source adapters
    → Project → relevance / negative gate → scoring только прошедших отбор
    → cross-source дедупликация → сортировка по score/свежести
    → state: проверка дубля → резервирование pending
    → шаблон отклика + HTML formatter → Telegram Bot API
    → подтверждение sent → атомарная запись JSON
```

`jobradar/sources/base.py` определяет контракт `SourceAdapter.fetch/parse`.
`parse` не выполняет сетевых запросов. `runner.py` изолирует сбои источников и
связывает scoring, state и доставку. Все внешние HTTP-взаимодействия синхронные;
параллельный парсинг и фоновые процессы здесь не нужны.

Единая модель `Project`:

| Поле | Тип / смысл |
|---|---|
| `source`, `source_id` | Обязательные строки, вместе образуют ключ дедупликации. |
| `title`, `url` | Обязательные; очищенный заголовок и проверенный HTTPS URL. |
| `description`, `category` | Строки или `None`. |
| `published_at` | timezone-aware `datetime` в UTC или `None`. |
| `budget_min`, `budget_max` | `Decimal` или `None`; в JSON строки для точной передачи суммы. |
| `currency` | Код RUB/USD/EUR/UAH либо `None`. |
| `responses_count`, `views_count` | Неотрицательные целые числа либо `None`. |
| `channel`, `external_url` | Telegram channel и внешняя ссылка на исходный заказ, если есть. |
| `origin_kind` | marketplace / direct_post / repost — приоритет при дедупликации. |
| `discovery_skip_reason` | Реклама, обучение или full-time пост; не допускается к scoring. |
| `fingerprint` в JSON | SHA-256 от нормализованного заголовка и нормализованной исходной ссылки. |

Неизвестные данные не заменяются нулём. Почасовые/помесячные ставки не выдаются
за полный бюджет. Числа бюджета извлекаются только из соответствующего блока
карточки, а не из произвольных чисел в описании. Ссылки карточек принимаются
только по HTTPS и только с хоста своего источника, без credentials и нестандартных портов.

Время Freelance.ru без зоны интерпретируется как МСК (UTC+3). Относительное время
ленты FL.ru служит только предварительным фильтром; для допуска нужна абсолютная
дата «Опубликован» в исходной карточке (МСК). Telegram сохраняет ISO timestamp
поста с зоной, но он не подтверждает дату исходного заказа.
Одна календарная дата, «вчера» или округлённое число дней не считаются достоверным
временем для 24-часового gate: published_at=None и отправка запрещена. Это касается
и сохранённого адаптера Weblancer. Будущее время также блокирует отправку.

Cross-source дедупликация объединяет текущую выборку и проверяет постоянную историю. Совпадения:
source:id, канонический URL, fingerprint. Для URL удаляются tracking-параметры,
fragment и slug биржевого заказа; содержательные query-параметры сохраняются.
Биржа выигрывает у прямого поста, прямой пост — у репоста. Исходная дата не
заменяется датой репоста. Для Telegram direct_post означает отсутствие явной
пересылки/внешней ссылки, а не подтверждение авторства заказчика.

Точный достаточно длинный заголовок используется как запасной признак, только
если нет конфликтующих исходных URL. Короткие заголовки вроде «Python» не сливаются.
Внешние короткие ссылки не раскрываются сетевыми запросами. Общая ссылка на
сервис сама по себе не объединяет разные заголовки. Разные формулировки без
исходных ссылок могут оставить дубли; semantic/LLM dedup не используется.
State v1 мигрирует в памяти в v2 с постоянной fingerprint history. `check`
оставляет реальный файл без изменений. Известный source:id или исходная ссылка
блокируют повтор даже когда исходного заказа уже нет в текущей выборке.

## Профиль и scoring 0–10

Профиль: Telegram bots, Python, REST API, n8n, автоматизация, парсинг,
JavaScript/React, исправление ошибок, небольшие веб-приложения, Docker/Linux,
интеграции с 1С. Целевой заказ: 5 000–30 000 RUB, примерно 1–5 дней.

До scoring обязательны два фильтра в `filtering.py`:

- Хотя бы один сильный технический термин (Python, API, бот, React, SQL и др.)
  или явно техническая категория. Явная разработка программного продукта вроде
  «Создать SaaS marketplace from scratch» также распознаётся без указанного стека.
- Основная задача не должна быть ручным заполнением карточек/анкет/таблиц,
  копирайтингом, отзывами, презентациями, ретушью, переводом, контентом, продажами,
  поиском клиентов, звонками, дизайном без разработки или работой оператора.
  Автоматизация этих процессов остаётся: «автоматизировать карточки через API»
  проходит; «заполнить карточки вручную» — нет. Намерение может быть в описании.

Одного слова Telegram недостаточно: рассылка готового контента не становится
разработкой. «Разработать Telegram-бота» проходит. Регистр и распространённые
русские окончания учитываются; «бот» не совпадает с «работа», `api` — с `capital`.
У отклонённых `relevance_gate=false`, `scored=false`, решение SKIP; scoring не
вызывается. В JSON нулевой score является служебным значением; текстовый вывод
показывает «scoring не выполнялся».

| Правило | Баллы |
|---|---:|
| Базовая оценка технического проекта | +2 |
| Совпадения с группами специализаций | +2…+4; только категория/продукт без стека +1 |
| STACK_COMPATIBILITY: HIGH_MATCH / PARTIAL_MATCH / LOW_UNKNOWN_MATCH | +2 / 0 / −3 |
| Возраст 0–2 / >2–6 / >6–12 / >12–24 часов | +3 / +2 / +1 / 0 |
| Старше `MAX_PROJECT_AGE_HOURS` (24 по умолчанию) | Hard SKIP |
| Описание ≥80 символов с конкретным действием/форматом результата | +1 |
| Бюджет меньше 3 000 RUB | Hard SKIP |
| Бюджет 3 000–4 999 / 5 000–30 000 / >30 000–100 000 RUB | −2 / +2 / +1 |
| Бюджет >100 000 RUB | 0 и LARGE_PROJECT |
| Бюджет неизвестен или не в RUB | 0 |
| Нет достоверного времени публикации / дата в будущем | Hard SKIP |
| Отклики 0–3 / 4–7 / 8–15 / 16–20 / 21–30 / 31+ | +3 / +2 / +1 / −1 / −3 / −5 |
| Доработка/исправление существующего проекта | +1 |
| Явно указан срок 1–5 дней | +1 |
| Срок >10, но <30 дней | −2 |
| LARGE_PROJECT | −3 один раз за флаг |
| EXPERIENCE_GATE | −3 один раз за флаг |

LARGE_PROJECT: marketplace, mobile app, SaaS, CRM/ERP с нуля, срок 30+ дней,
enterprise/ERP внедрение или бюджет >100 000 RUB. EXPERIENCE_GATE: требуется
3+ года опыта, обязательные кейсы, подтверждённые внедрения, рекомендации клиентов,
Senior only. Флаги снижают оценку и видны в причинах и уведомлении; сами по себе
они не запрещают GOOD. Наивысшая оценка при LARGE_PROJECT/EXPERIENCE_GATE,
возрасте >6 часов, 21–30 откликах или OPEN_STATUS_UNKNOWN — 7.
При 31+ откликах оценка не выше 6. Неизвестное число откликов — максимум GOOD 7,
без автоматической отправки. Все ограничения применяются совместно и не повышают score.
При hard skip по дате, закрытому статусу, ссылке или бюджету итог не выше 5 и `eligible=false`.

### Обязательная STACK_COMPATIBILITY

`jobradar/stack.py` определяет совпадение по заголовку и описанию, отдельно от
relevance gate. Техническая категория сама по себе не подтверждает стек.
Значение присутствует даже у SKIP; отклонённые relevance gate проекты по-прежнему
не получают числовой scoring. Для прошедших gate поправка применяется один раз
к raw_score, до общих ограничений. Повторение ключевых слов не умножает бонус.

| Уровень | Технологии | Поправка |
|---|---|---:|
| HIGH_MATCH | Python, Telegram Bot API, aiogram, FastAPI, REST API, webhooks, n8n, automation, parsing/scraping, JavaScript, TypeScript, React, Node.js, Docker, Linux, VPS, SQL/PostgreSQL | +2 |
| PARTIAL_MATCH | Интеграции/API/обмен/простые расширения и программирование 1С, PHP, WordPress, OpenCart, платёжные интеграции, Google APIs, Bitrix | 0 |
| LOW_UNKNOWN_MATCH | Tilda, Android, Ruby/Rails, Java, C#, C++, Flutter, Kotlin, Swift, Cleverence, GetCourse; другой явно обязательный неподтверждённый стек или отсутствие сведений о стеке | −3 |

При смешанных требованиях приоритет консервативный: LOW/UNKNOWN → PARTIAL → HIGH.
Java + JS остаётся LOW/UNKNOWN; OpenCart + REST API — PARTIAL; Cleverence + 1С —
LOW/UNKNOWN. JavaScript не совпадает с Java. Явные «Java не требуется» или «без Java»
не считаются требованием Java; «опыт Java не требуется» не исключает сам язык.
Все задачи 1С — максимум PARTIAL. Простая интеграция/API/обмен/расширение —
максимум GOOD 7. Перенос полноценной конфигурации, сложные ERP-модули, крупное
внедрение или архитектура конфигурации добавляют `DEEP_1C`: максимум GOOD 6,
complexity минимум 6. Отклик не заявляет подтверждённый опыт 1С-разработчика.
Windows/RDP, Go, Rust, Elixir и другие явно названные обязательные технологии вне
профиля не получают HIGH только из-за соседнего слова API или VPS.

LOW/UNKNOWN добавляет `STACK_MISMATCH`, ограничивает score до **6/10** и запрещает
FIRE независимо от бюджета и других бонусов. Если после штрафа score ниже 6,
решение — SKIP, а не принудительное повышение до GOOD. Сложность такого технического
проекта — минимум **6/10**. Ограничения возраста и остальные hard gates сохраняются.
PARTIAL_MATCH ограничивает score до **7/10**, FIRE запрещён.

Отклик для LOW/UNKNOWN предлагает уточнить используемый стек и характер доработок,
без утверждений об опыте и готовности немедленно приступить. Для PARTIAL используется
нейтральный запрос версии платформы и объёма работ. Ruby-задача больше не получает
шаблон «Работаю с JavaScript, React». Классификация rule-based: неуказанный стек не
угадывается, альтернативные/косвенные требования могут давать консервативный LOW.

Синонимы внутри одной группы и повторения слов не складываются. Для диапазона
бюджета используется верхняя граница; если есть только «от», используется она.
Так диапазон 1 000–6 000 RUB не считается бюджетом ниже 3 000. Это эвристика,
а не подтверждение суммы оплаты. Неизвестные отклики дают 0. Неизвестная/будущая
дата даёт 0 за свежесть и hard skip независимо от остальных бонусов.
`HOT_PROJECT_AGE_HOURS` задаёт отметку HOT и максимальное окно FIRE (не более 6 часов),
не меняя таблицу бонусов свежести. Границы включительны: ровно 6 часов ещё допускают
FIRE, ровно 24 часа — GOOD. Увеличение MAX не отменяет жёсткого предела 24 часа.

Сумма ограничивается диапазоном 0–10; `raw_score` сохраняет исходную сумму.
**8–10: FIRE / БРАТЬ; 6–7: GOOD / ПОСМОТРЕТЬ; 0–5: не отправлять.**
Это диагностическое решение; GOOD 6 по умолчанию остаётся только в check/watchlist.
Причины с кодами и баллами доступны в `check --json` и сохраняются в state для
отправленных/зарезервированных заказов. Уведомление показывает основные плюсы и риски.

Сложность — отдельная эвристика 1–10, а не расчёт трудозатрат. Рекомендуемая
цена использует ориентиры 5–10 / 10–20 / 20–30 тысяч RUB по сложности и учитывает
пересечение с бюджетом заказчика. Если пересечения нет, нужно уточнить объём.
Иностранная валюта не пересчитывается по выдуманному курсу. Наличие бюджета в
USD/EUR не даёт бюджетного бонуса и не запускает рублёвый hard skip.

### Final quality gate перед Telegram

По умолчанию автоматически допускаются только новые проекты:

| Решение | Условия |
|---|---|
| FIRE | score ≥8, HIGH_MATCH, подтверждённый приём откликов, responses ≤20 |
| GOOD | score ≥7, HIGH_MATCH или PARTIAL_MATCH, responses ≤20 |
| GOOD 6 / STACK_MISMATCH | Без автоматической отправки; доступны в диагностике |

Проверка выполняется до резервирования `pending` и повторно перед отправкой
с актуальным временем. Возраст, статус закрытия, прямая ссылка, публикация и
дедупликация продолжают блокировать отправку независимо от настроек качества.
GOOD 7 с неизвестным открытым статусом допускается при выполнении остальных
условий; FIRE без подтверждения запрещён. Неизвестные отклики не считаются нулём.

Настройки по умолчанию уже работают при отсутствии новых строк в существующем `.env`:

```dotenv
TELEGRAM_MIN_SCORE=7
TELEGRAM_MAX_RESPONSES=20
TELEGRAM_ALLOW_STACK_MISMATCH=false
```

Порог можно явно изменить: score 6–10, responses 0–10000. Разрешение mismatch
не снимает потолок score 6: для доставки такого проекта нужно также явно снизить
минимальный score до 6. Эти настройки не меняют label/caps и hard safety gates.
При responses >50 действует дополнительный запрет, кроме HIGH_MATCH с известным
бюджетом ≥50 000 RUB (нижняя граница диапазона, иначе единственная известная).
Это исключение снимает только дополнительный запрет >50; оно не обходит минимальный
score и настроенный лимит откликов. Поэтому при стандартных 7/20 даже такой
дорогой проект с 55 откликами не отправляется.

## Telegram: создать бота и получить chat ID

1. Откройте официального [@BotFather](https://t.me/BotFather) в Telegram.
2. Отправьте `/newbot`, задайте название и уникальный username, заканчивающийся на `bot`.
3. Сохраните выданный токен. Не добавляйте его в Git, README, скриншоты или логи.
4. Откройте своего бота и отправьте ему `/start` — бот не может первым начать личный чат.
5. Создайте `.env` только если его ещё нет. Заполните `TELEGRAM_BOT_TOKEN` вручную
   в локальном текстовом редакторе. `TELEGRAM_CHAT_ID` пока оставьте пустым.
6. Выполните `python -m jobradar telegram-chat-id`. Команда читает токен из `.env`,
   вызывает `getUpdates` и выводит по одной JSON-строке на чат: только `chat_id`,
   `type` и `username`, если доступен. Chat ID заранее не требуется. Сообщения,
   имена, токен и сырые ответы сервера не печатаются. Команда ничего не отправляет
   и не меняет `.env` или state. Старый `python scripts/get_chat_id.py` вызывает
   эту же CLI-команду для совместимости.
7. Выберите строку своего аккаунта и добавьте числовое положительное значение
   `TELEGRAM_CHAT_ID` в `.env`. Не используйте ID группы, канала или чужого пользователя.
8. Выполните `python -m jobradar test-telegram`, затем `python -m jobradar run`.

Если сообщений нет, команда выводит:

> Откройте бота в Telegram, нажмите Start или отправьте сообщение и повторите команду.

При успехе пример вывода на вымышленных данных:

```json
{"chat_id": 123456, "type": "private", "username": "owner_example"}
```

Команда читает до 100 ожидающих updates и показывает чаты по свежести сообщений
в полученной порции, без дублей. При большой очереди это не вся история: команда
не подтверждает updates, не применяет отрицательный offset и не удаляет более старые
сообщения ради получения конца очереди. Не подключайте к тому же боту webhook/другой
polling-сервис во время настройки. При конфликте 409 будет инструкция; webhook
автоматически не удаляется. Фильтр `allowed_updates` тоже не меняется.

Токен не передаётся через аргументы командной строки, не запрашивается в консоли
и не вставляется в адресную строку браузера. Заполняйте его только в своём `.env`;
в чат Codex токен присылать не нужно. `.gitignore` исключает `.env`, `*.env`, их
локальные варианты/резервные копии, `__pycache__`, каталоги секретов и файлы ключей.
`.env.example` остаётся доступным для Git. Реальный `.env` не включайте и в ZIP.

### Команды

```bash
python -m jobradar check          # только чтение и оценка
python -m jobradar run            # новые подходящие проекты → владелец
python -m jobradar test-telegram  # одно тестовое сообщение, state не меняется
python -m jobradar telegram-chat-id  # только ID, тип и username чатов из getUpdates
```

Реальный `run` при первом запуске отправит подходящие заказы текущих discovery
страниц, не старше установленного порога, максимум 10 сообщений. Неизвестная,
неполная или будущая дата запрещает отправку. Старые объявления с поднятием в ленте
могут попасть в проверку; исходная старая дата блокирует их отправку.

Структурированные логи JSON идут в stderr; результаты `check` — в stdout.
В логах нет тела ответов Telegram, токенов, chat ID и traceback HTTP-запросов.
При сетевой ошибке Telegram записывается событие `telegram_network_error` с полями
`telegram_endpoint` (`getMe`, `getUpdates` или `sendMessage`), `exception_type`
и очищенным `message`. URL, токен и chat ID удаляются до записи; тела HTTP/API ошибок
не выводятся. Для ошибок HTTP логируется только endpoint и HTTP status.
Коды завершения: `0` — успех; `1` — ошибка источника/доставки при обработке;
`2` — конфигурация, повреждённый state или другой фатальный сбой; `130` — прерывание.

### Сетевое окружение Telegram

Telegram и публичные источники используют обычный `httpx.Client(timeout=20)`:
стандартный transport, включённую проверку TLS и настройки окружения HTTPX.
Проект не подменяет proxy, сертификаты, base URL и не задаёт `trust_env=False`.
Настроенные HTTP_PROXY/HTTPS_PROXY/ALL_PROXY, NO_PROXY и SSL_CERT_FILE/SSL_CERT_DIR
учитываются стандартным HTTPX. Их значения в диагностические логи не попадают.
См. [документацию HTTPX](https://www.python-httpx.org/environment_variables/).

Ранее `trust_env=False` принудительно отключал настроенный прокси. Это объясняло
ситуацию, когда прямой вызов HTTPX работал, а CLI проекта получал ConnectTimeout.
Лимит подключения раньше составлял 5 секунд; теперь все сетевые таймауты клиента —
20 секунд, как в прямом проверенном вызове. Лимиты размеров ответов и запрет redirect
сохраняются. Неопределённые ошибки POST по-прежнему не повторяются автоматически.

## Дедупликация, pending и ограничения доставки

`data/state.json` версии 2 содержит `entries` по `source:source_id` и постоянный
словарь `fingerprints`. В fingerprint history сохраняются `source`, `source_id`,
`normalized_url`, `first_seen_at`, `sent_at`, `status` (`seen`/`pending`/`sent`).
Tracking-параметры и slug FL.ru не меняют идентичность заказа; смена заголовка
при прежней ссылке также не разрешает повторную отправку. Копия из другого
источника с той же прямой ссылкой блокируется и после перезапуска.
`first_seen_at` — первое наблюдение в сохраняющем state запуске `run`;
`check` ничего не добавляет в историю. `sent_at` записывается только после успеха.
Повторный `mark_sent` не изменяет дату уже подтверждённой доставки.
Версия 1 читается и мигрирует в памяти без записи; на диске версия изменится
при следующей разрешённой записи `run`. Для старых записей без URL известные
канонические ссылки FL.ru/Freelance.ru/Habr восстанавливаются по source_id;
для остальных сохраняется защита по source:id. Ранее удалённые записи не восстановить.

Обычная отправленная запись содержит `source`, `source_id`, `status=sent`,
`reserved_at`, `sent_at` и `assessment` с причинами оценки. Токен и chat ID
никогда не попадают в state. Этот файл намеренно отслеживается Git.

Перед POST в Telegram заказ атомарно записывается как `pending`. После
подтверждённого успеха — как `sent`. При явном отказе (например, 403 или исчерпанный
429) резерв снимается. При read timeout, обрыве после отправки, 5xx или неполном
подтверждении результат может быть неизвестен: `pending` остаётся, повторной
автоматической отправки нет. Повторяются только безопасные ошибки подключения
и явный 429 с коротким Retry-After. Есть пауза 1,1 секунды между уведомлениями.

Чтобы разобрать `pending`, остановите запуск, найдите соответствующий заказ
в чате и state. Если сообщение есть, согласованно установите `status=sent` и
`sent_at` в ISO-формате с зоной в `entries` и соответствующей записи `fingerprints`.
Если уверены, что сообщения нет, удалите только pending из `entries` и переведите
связанную историю в `seen`, сохранив `first_seen_at` и `sent_at=null`.
Несогласованный state блокирует запуск. В Actions сначала сохраните исправленный
state в default branch. Не удаляйте подтверждённую историю ради повторной отправки.

Запись state выполняется через временный файл, fsync и атомарный replace.
Повреждённый state не сбрасывается автоматически — отправка останавливается.
`data/state.json.lock` предотвращает два локальных `run` с одним state. После
аварийного завершения удаляйте оставшийся lock только когда процесс точно остановлен.

Подробные `entries` ограничены 10 000 записями. При переполнении удаляются старейшие
`sent` из entries, но их компактная fingerprint history остаётся навсегда.
Pending не удаляется; слишком много pending требует ручного разбора. Постоянная
история не имеет TTL и не вытесняется лимитом. Файл больше 256 MiB блокирует
чтение и отправку, вместо молчаливого забывания истории. После очистки/отката
state или при запуске независимых копий дубли возможны. Не запускайте
одновременно локальный `run` и Actions с разными копиями state.

**Абсолютное exactly-once между Telegram и Git невозможно в этой схеме.**
У `sendMessage` нет ключа идемпотентности: runner может аварийно завершиться после
доставки, но до push обновлённого state. `pending`, атомарная запись, concurrency
и commit после частичного сбоя уменьшают этот риск, но не превращают два внешних
сервиса в одну транзакцию. Успешный повторный обычный запуск с тем же state
проверен тестами: повторной отправки нет.

## GitHub Actions без VPS

   добавьте `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`.
3. Разрешите GitHub Actions и запись `GITHUB_TOKEN` в contents. Workflow запрашивает
   `contents: write`. Правила защиты default branch должны позволять этому workflow
   коммитить `data/state.json`; обходить защиту force-push или личным токеном код не будет.
4. В **Actions → Mollix Job Radar → Run workflow** выберите default branch
   и запустите вручную. Проверьте тесты, Telegram и коммит состояния.
5. После этого schedule запускается каждые 10 минут на минутах 3/13/23/33/43/53 UTC.

Порядок: checkout актуальной default branch → Python 3.12 → pip install → pytest →
офлайн dry-run → `run` → commit state, только если изменился.
Commit message: `chore: update job radar state [skip ci]`.
Workflow имеет только `schedule`/`workflow_dispatch`, без `push`, поэтому этот
коммит не запускает его повторно. Общая concurrency-группа и `cancel-in-progress: false`
не позволяют двум Actions-запускам отправлять одновременно. Запуск вручную с другой
ветки пропускается, чтобы не использовать отдельную историю отправок.

Сохранение state выполняется также после частичного сбоя `run`. При конфликте
коммитов — обычный rebase, без force-push; при неразрешимом конфликте job завершается
ошибкой. Неудачный job сохраняет state как Actions artifact на 7 дней. Если push
не прошёл, приостановите workflow, восстановите этот state в default branch и
только потом возобновляйте расписание. При жёстком убийстве runner artifact и
финальный шаг тоже могут не успеть выполниться.

Стандартные GitHub-hosted runners в **публичных репозиториях** бесплатны.
В приватных действуют квоты тарифа: при 144 запусках в сутки бесплатного лимита
может не хватить. Бот не включает платный биллинг и не покупает вычисления.
См. [GitHub Actions billing](https://docs.github.com/en/actions/concepts/billing-and-usage).

Schedule — не гарантия точного интервала: GitHub может задержать или пропустить
запуск при нагрузке. В публичном репозитории расписание может отключиться после
60 дней без активности. См. [ограничения schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

## Настройки

| Переменная | По умолчанию | Допустимо |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | нет | Только `.env` / Secrets; нужен для `telegram-chat-id`, `run` и `test-telegram`. |
| `TELEGRAM_CHAT_ID` | нет | Один положительный числовой ID личного чата владельца. |
| `TELEGRAM_MIN_SCORE` | 7 | Минимальная оценка для доставки, 6–10; GOOD 6 исключён по умолчанию. |
| `TELEGRAM_MAX_RESPONSES` | 20 | Лимит откликов для доставки, 0–10000; неизвестное число блокируется. |
| `TELEGRAM_ALLOW_STACK_MISMATCH` | false | Явное разрешение несовпадения стека; не обходит остальные gates. |
| `JOBRADAR_STATE_PATH` | `data/state.json` | Локальный путь. В workflow оставляйте этот путь: commit отслеживает именно его. |
| `JOBRADAR_MAX_SEND` | 10 | 1–50 за запуск. |
| `JOBRADAR_HISTORY_LIMIT` | 10000 | 100–50000 подробных entries; постоянная fingerprint history не очищается. |
| `MAX_PROJECT_AGE_HOURS` | 24 | Парсер принимает 1–720; safety gate применяет минимум значения и 24 часов. |
| `HOT_PROJECT_AGE_HOURS` | 6 | Парсер принимает 1…MAX_PROJECT_AGE_HOURS; FIRE/HOT ограничены минимумом значения, max age и 6 часов. |
| `FREELANCE_RU_ENABLED` | true | Публичная IT-категория и 10 тематических поисков. |
| `HABR_FREELANCE_ENABLED` | true | Сейчас проверка robots заканчивается `robots_disallowed`; лента не запрашивается. |
| `FL_RU_ENABLED` | true | Три проверенные публичные категории FL.ru. |
| `TELEGRAM_PUBLIC_ENABLED` | true | Только web preview; не использует Bot API или аккаунт пользователя. |
| `TELEGRAM_PUBLIC_CHANNELS` | freelansim_ru,digitaltender,job_for_bots,freelancetaverna | 1–20 публичных usernames через запятую, без @, URL и invite links. |
| `WEBLANCER_ENABLED` | false | `true` / `false`; включать только при легитимной доступности публичной ленты. |

Загружается только `.env` из текущей папки. Уже заданные environment variables
имеют приоритет. Родительские папки на наличие `.env` не просматриваются.
Поддерживается UTF-8 с BOM, который может добавить Windows-редактор.
Ключевые слова, правила и шаблоны доступны для редактирования в соответствующих `.py`.
Старая переменная `JOBRADAR_MAX_AGE_DAYS` больше не используется. Существующий
`.env` автоматически не переписывается: без новых переменных действуют 24/6,
Freelance.ru/Habr/FL.ru/Telegram public включены, Weblancer выключен.
При необходимости добавьте их вручную из `.env.example` без изменения секретов.

## Добавить source adapter

1. Проверьте доступность публичной ленты и robots.txt без входа, CAPTCHA и обходов.
2. Создайте `jobradar/sources/new_source.py` с подклассом `SourceAdapter`,
   уникальными `name`, каноническим HTTPS `url`, точным списком `allowed_hosts`.
3. Реализуйте `parse(html, *, now=None) -> list[Project]`. Используйте стабильный
   ID источника, `safe_url`, нормализаторы и nullable-поля. Не угадывайте неизвестные
   данные. Неизвестная разметка должна давать `SourceError` с постоянным безопасным кодом.
4. Создайте ручные sanitised fixtures с придуманным содержимым и тестами для
   хорошей/сломанной карточки, неверной ссылки, отсутствующих метаданных и пустой ленты.
5. Добавьте экземпляр в `configured_sources()`, настройку `<source>_enabled`, подпись в `SOURCE_LABELS`, fixture
   `<name>.html` и описание в README. Запустите pytest и `check` без отправки.

Счётчик `parse_errors` увеличивается на повреждённые карточки/страницы.
`fetch_pages` сохраняет частичный результат, проверяет robots через общий HTTP client
и удаляет повторы source:id/URL между страницами. Не подменяйте отсутствие времени
текущим временем загрузки. Для Habr живая HTML-разметка пока не верифицирована.

## Проверки и ограничения V1

Тесты офлайн: нормализация, все положительные/отрицательные ключевые слова,
scoring, дедупликация, повреждение/атомарная запись state, шаблоны, Telegram HTML,
HTTP MockTransport, robots, URL validation, лимиты ответов и изоляция источников.
В fixtures нет полного реального HTML, контактов пользователей или cookies.
Отдельно проведён настоящий сетевой `check --top`; текущий этап — `FINAL_QUALITY_REPORT.md`
и `final-quality-check.json`. `STACK_COMPATIBILITY_REPORT.md`, `FINAL_SAFETY_REPORT.md`, `DISCOVERY_REPORT.md`, `RELEVANCE_FIX_REPORT.md`, `REPORT.md` и
`NETWORKING_FIX_REPORT.md` относятся к предыдущим этапам.

- FL.ru: не более трёх страниц на раздел и 20 дополнительных карточек кандидатов
  за запуск. За пределами лимитов свежие заказы могут быть пропущены. Freelance.ru:
  первая разрешённая страница каждого поиска; пагинация сейчас запрещена robots.
  Telegram: последняя доступная порция; RSS не используется.
- Закреплённые, поднятые и рекламные карточки могут занимать места новых заказов.
  Предпросмотр описания бывает усечённым; Weblancer не даёт точного времени публикации.
- Изменение HTML, антибот-защита или доступность с IP GitHub Actions могут нарушить
  получение данных. Локальная доступность не гарантирует доступность на runner.
- Отбор и scoring используют эвристики: неоднозначные формулировки и смешанные
  ручные/технические задачи могут классифицироваться неверно. Длительность,
  сложность и цена — предварительные ориентиры.
- Набор поисковых слов/категорий конечен. Premium-карточки недоступны, Weblancer
  выключен, Habr блокируется robots. Подключённый публичный канал может давно
  не обновляться, содержать рекламу или обычные вакансии; доступность не означает
  наличие подходящих свежих заказов. Пост с несколькими заказами считается одним.
- Требования к опыту, масштаб и смежные технологии могут быть описаны косвенно.
  Прочитайте оригинал и отредактируйте отклик перед отправкой заказчику.
- Гарантия от дублей ограничена сохранённой историей и непрерывностью state.
  `pending` иногда означает пропущенное уведомление и требует ручного разбора.
- Постоянная дедупликация использует известный source:id, fingerprint и URL.
  Короткие ссылки не раскрываются; один заказ, заново опубликованный с другим
  ID, другой ссылкой и заголовком, нельзя надёжно отождествить эвристикой.
- Это один владелец и один state, без интерактивных команд, кабинета, веб-сервера
  и нескольких пользователей. Telegram-сообщения отправляются только по явному `run`.

V1 не использует платный AI, потому что rule-based scoring и шаблоны позволяют
получить работающий радар без стоимости токенов, внешней передачи ТЗ LLM и скрытой
логики оценки. Позднее AI можно добавить отдельно, сохранив эти правила как baseline.
